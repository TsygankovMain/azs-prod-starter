# Спека: «Профили рассылки» (гибкое расписание)

**Версия:** 1.1  
**Дата:** 2026-06-15  
**Статус:** Черновик — продуктовые решения OR-1–OR-4 зафиксированы; открыты технические вопросы по эскалации (см. раздел 8)

---

## 1. Проблема и цели

### Что болит сейчас

В текущей архитектуре существует **единое глобальное расписание** на все АЗС портала:
- `settings.report.dispatchTimes` — список времён HH:MM, **единый для всех** АЗС
- `settings.report.dispatchJitterMinutes` — джиттер, **одинаковый для всех** АЗС
- Нет способа задать разное расписание для разных АЗС (например, городские vs трассовые)

**Клиентский запрос**: «присылать отчёты НЕ в часы пик» — например, не в 11:00–13:00 и не в 17:00–19:00. Текущая модель со слотами + джиттером это не поддерживает: джиттер только сдвигает момент, но не исключает диапазон.

**Следствия:**
- Городские АЗС с большим потоком в пик не могут получить расписание «вне пика»
- Трассовые АЗС могут иметь другой рабочий ритм, не совпадающий с общим расписанием
- Администратор не может сгруппировать АЗС и задать им разную логику отправки

### Цели фичи

1. Дать администратору возможность объединить произвольный набор АЗС в «профиль рассылки» с собственным расписанием.
2. Поддержать **два режима**: классические фиксированные слоты (Режим A) и случайное время внутри заданных окон (Режим B, «не в часы пик»).
3. Не сломать существующую логику: текущее глобальное расписание → профиль «По умолчанию», всё работает без изменений конфигурации.

## 2. Как работает сейчас (текущая модель)

### 2.1 Настройки расписания

Файл: `backends/node/api/src/settings/defaultSettings.js`

```
// строки 44-45, 53
report: {
  dispatchTimes: [],                    // массив 'HH:MM' — слоты отправки
  dispatchJitterMinutes: 15,            // ±N минут случайного сдвига
  workWindow: { start: '07:00', end: '22:00' },  // ограничение (clamping)
}
timezone: 'Europe/Moscow'              // таймзона для всего портала
```

Нормализация (`defaultSettings.js:145–169`): `normalizeDispatchTimes()` — убирает дубли, сортирует, приводит к `HH:MM`. Валидация (`defaultSettings.js:231–268`): массив `HH:MM`, `dispatchJitterMinutes >= 0`, `workWindow.start < workWindow.end`.

### 2.2 Генерация дневного плана

Файл: `backends/node/api/src/dispatch/dispatchPlanGenerator.js`

```
// строки 212-270: generateDailyPlan()
for (const candidate of candidates) {            // перебор всех активных АЗС
  for (const baseTime of baseTimes) {            // перебор всех слотов
    const jitterMinutes = pickJitterMinutes(...)  // случайный ±N минут

      planDate, baseTime, jitterMinutes,
      workWindow,    // clamping — execute_at не выходит за границы
      timezone       // 'Europe/Moscow' — вся арифметика в зоне портала

    await planStore.upsertPlanned({ ..., baseTime, executeAt, jitterMinutes })
```

`buildZonedDatetime()` (`dispatchPlanGenerator.js:87–98`): строит UTC-момент для wall-clock HH:MM в заданной таймзоне через `Intl.DateTimeFormat`. Правильно обрабатывает Europe/Moscow (UTC+3, без DST).

`computeExecuteAt()` (`dispatchPlanGenerator.js:172–192`): base + jitter, clamp по workWindow.

## 3. Модель «Профили рассылки»

### 3.1 Структура данных (JSON-схема)

Новое поле `dispatchProfiles` добавляется в корень настроек (рядом с `report`, `timezone`):

```json
{
  "dispatchProfiles": [
    {
      "id": "profile-uuid-or-slug",
      "name": "Трассовые АЗС (не в пик)",
      "azsIds": ["42", "117", "234"],
      "mode": "B",
      "config": {
        "windows": [
          { "from": "06:00", "to": "10:00" },
          { "from": "13:00", "to": "16:00" },
          { "from": "21:00", "to": "23:59" }
        ],
        "countPerDay": 1
      },
      "timezone": null
    },
    {
      "id": "profile-city",
      "name": "Городские АЗС",
      "azsIds": ["7", "88"],
      "mode": "A",
      "config": {
        "slots": ["09:00", "17:00"],
        "jitterMinutes": 10
      },
      "timezone": null
    }
  ]
}
```

**Поля профиля:**

| Поле | Тип | Обязательно | Описание |
|------|-----|------------|---------|
| `id` | string | да | UUID или человекочитаемый slug, уникальный |
| `name` | string | да | Название профиля (отображается в UI) |
| `azsIds` | string[] | да | Список ID карточек АЗС из CRM |
| `mode` | `"A"` \| `"B"` | да | Режим расписания |
| `config` | object | да | Конфиг режима (структура зависит от mode) |
| `timezone` | string \| null | нет | IANA-таймзона; null → берётся `settings.timezone` |

**Конфиг режима A (слоты + джиттер):**

```json
{
  "slots": ["09:00", "17:00"],
  "jitterMinutes": 15
}
```

**Конфиг режима B (1 отчёт/день с эскалацией по окнам):**

```json
{
  "windows": [
    { "from": "06:00", "to": "10:00" },
    { "from": "13:00", "to": "16:00" },
    { "from": "21:00", "to": "23:59" }
  ],
  "escalateUntilDone": true
}
```

Поля конфига режима B:

| Поле | Тип | Обязательно | Описание |
|------|-----|------------|---------|
| `windows` | `[{from, to}]` | да | Упорядоченный список окон HH:MM. Порядок определяет: окно[0] — первичная отправка, окна[1..N-1] — точки эскалации |
| `escalateUntilDone` | boolean | нет | Включить эскалацию (повторный запрос во вторых и последующих окнах, если отчёт ещё не сдан). По умолчанию: `true` |

> **Удалено поле `countPerDay`**: смысл изменился — в режиме B всегда создаётся **ровно 1 отчёт (1 CRM-карточка) в день**. Несколько уведомлений — это эскалация существующего отчёта, а не создание новых. Если нужно «несколько отчётов в день» — это режим A с несколькими слотами (вне scope v1).

### 3.2 Профиль «По умолчанию»

АЗС, не попавшая ни в один явный профиль, автоматически получает расписание из **профиля «По умолчанию»** — он не хранится в `dispatchProfiles` явно, а строится на лету из текущих `settings.report.dispatchTimes`, `settings.report.dispatchJitterMinutes`, `settings.report.workWindow`. Это обеспечивает полную обратную совместимость.

### 3.3 Резолвинг профиля для АЗС

При генерации дневного плана для каждой АЗС применяется следующая логика:

```
function resolveProfileForAzs(azsId, dispatchProfiles):
  for profile in dispatchProfiles:
    if azsId in profile.azsIds:
      return profile
  return DEFAULT_PROFILE  // из settings.report.*
```

**Инвариант (OR-4, РЕШЕНО)**: каждая АЗС принадлежит **максимум одному** явному профилю. АЗС, не вошедшая ни в один профиль, автоматически получает профиль «По умолчанию». UI блокирует добавление АЗС в два профиля одновременно (занятые АЗС отображаются серыми/disabled в мультиселекте). Бэкенд-валидация при `PUT /api/settings` возвращает 400, если одна `azsId` встречается в двух профилях.

### 3.4 Таймзона профиля

Если `profile.timezone` не задана (null), используется глобальная `settings.timezone`. Это позволяет задавать локальную таймзону для конкретной группы АЗС (например, АЗС в Сибири), не меняя глобальную настройку.

## 4. Режим A и Режим B — точная семантика

### 4.1 Режим A «Слоты + джиттер» (существующее поведение)

**Параметры:** `slots: string[]` (HH:MM), `jitterMinutes: number`.

**Алгоритм (один слот, одна АЗС):**
1. `baseTime = slot` (HH:MM → HHMM)
2. `executeAt = buildZonedDatetime(planDate, baseTime, timezone)` — UTC-момент wall-clock в таймзоне
3. `jitter = pickJitterMinutes(jitterMinutes, rng)` — равномерно из [-N, +N]
4. `executeAt += jitter * 60_000`
5. (опционально) clamp по workWindow: если executeAt < windowStart → windowStart; если > windowEnd → windowEnd
6. `slotKey = buildSlotKey({ slotDate: planDate, slotHHmm: baseTime })`

**Идемпотентность**: slotKey строится по baseTime (фиксированное), не по executeAt (случайное). Повторная генерация того же дня не создаёт дубликатов.

Этот алгоритм уже реализован в `generateDailyPlan()` (`dispatchPlanGenerator.js:212–270`) и `dispatchService.js`. Для режима A изменений в логике нет — только вызов с конфигом профиля вместо глобальных настроек.

### 4.2 Режим B «1 отчёт в день с эскалацией по окнам» (РЕШЕНО OR-1)

**Продуктовая формулировка (дословно, зафиксировано):**
«1 отчёт/день, но если не сдан в первом слоте — обязательно спросить повторно во втором.»

**Параметры:** `windows: [{from, to}]` (HH:MM, упорядоченный массив), `escalateUntilDone: boolean` (дефолт: `true`).

**Ключевой принцип**: в день создаётся **ровно 1 отчёт (1 CRM-карточка)**. Несколько уведомлений — это переотправка напоминания по одному и тому же отчёту (эскалация), а не новые карточки.

#### 4.2.1 Шаги алгоритма (итог дня)

1. **Окна упорядочены**: `windows[0]` — первичная отправка, `windows[1]`, `windows[2]`, … — точки эскалации.

2. **Первичная отправка (окно[0]):** в случайный момент внутри `windows[0]` (детерминированный seed = `hash(planDate + ":" + azsId)`) генератор создаёт в плане **«первичную точку»**. При её исполнении `dispatchService.dispatchCandidate()` (`dispatchService.js:125`) создаёт CRM-карточку (`bitrixClient.createReportItem`) и отправляет уведомление боту (`notificationService.notifyDispatch`).

3. **Точки эскалации (окна[1..N-1]):** для каждого последующего окна генератор добавляет в план **«напоминание-точку»** — запись с `slotKey = buildSlotKey({planDate, slotHHmm}) + ":reminder:" + windowIndex` (суффикс индекса обеспечивает идемпотентность каждой точки отдельно). При наступлении напоминания-точки исполнитель (новый хелпер в `dispatchScheduler.js`) **проверяет статус отчёта**: если статус `done` или `submitted` → пропускает уведомление. Если отчёт ещё не сдан → вызывает `notificationService.notify()` с повторным запросом по **тому же** `reportItemId`/`reserveId` (новую карточку НЕ создаёт).

4. **Цепочка эскалации:** каждое последующее окно повторяет проверку. Уведомление доходит только до первого «сдан». После сдачи все оставшиеся напоминание-точки дня автоматически пропускаются.

5. **Итог**: 1 отчёт (1 карточка) в день, до N уведомлений (1 первичное + до N-1 условных напоминаний), пока не сдан.

#### 4.2.2 Дедлайн в режиме B (РЕШЕНО, согласование с BUG-024)

**Дедлайн = конец последнего окна дня (+ опциональный грейс).**

Это переопределяет текущую формулу BUG-024 (`dispatchService.js:201`: `effectiveBase = max(scheduledAt, now) + timeoutMinutes`) — для режима B `deadlineAt` устанавливается не от момента отправки + timeout, а равен моменту конца `windows[N-1]` (+ грейс, если задан).

**Мотивация:** если установить дедлайн как `t1 + timeoutMinutes`, `timeoutWatcher.runOnce()` (`timeoutWatcher.js:38–97`) пометит отчёт как «просрочен» ещё до наступления `windows[1]`, и эскалация станет бессмысленной.

**Реализация:** при создании отчёта в «первичной точке» вычисляется:
```
lastWindowEnd = buildZonedDatetime(planDate, windows[N-1].to.replace(':',''), tz)
// graceMinutes: ⚠️ к подтверждению (предлагаем 0 по умолчанию, с возможностью задать в конфиге)
deadlineAt = addMinutes(lastWindowEnd, graceMinutes)
```
Это значение передаётся в `buildReportFields()` (`dispatchService.js:84`) и в `dispatchLogStore.markDone()` (`dispatchService.js:219`).

#### 4.2.3 Встраивание в генератор плана и планировщик

**`generateDailyPlan()` (`dispatchPlanGenerator.js:212–270`)** — место для изменения цикла `for (const candidate of candidates)` (`dispatchPlanGenerator.js:232`):

- Для режима B вместо одного прохода по слотам — два вида строк в плане:
  - **Первичная точка**: `baseTime = pickRandomMomentInWindows(planDate, azsId, [windows[0]], tz)`, тип записи = `'primary'`
  - **Напоминание-точки** (по одной на `windows[1..N-1]`): `baseTime = pickRandomMomentInWindows(planDate, azsId, [windows[i]], tz)`, тип записи = `'reminder'`, `windowIndex = i`
- `planStore.upsertPlanned()` (`dispatchPlanGenerator.js:252`) вызывается для каждой точки с новым полем `entryType: 'primary' | 'reminder'` и `windowIndex: number`.

**`dispatchScheduler.js` — исполнитель (строки ~796–816 — крон-задача, место добавления):**

В минутном тике, когда точка плана готова к исполнению, исполнитель проверяет `entryType`:
- `'primary'` → существующая логика `dispatchService.dispatchBatch()` → создаёт карточку и шлёт уведомление.
- `'reminder'` → новая ветка: `reportsStore.getBySlotKey(originalSlotKey)` → проверка `status !== 'done' && status !== 'submitted'` → если не сдан → `notificationService.notify(...)` с текстом-напоминанием и `reportItemId`.

#### 4.2.4 Идемпотентность напоминаний

Напоминание-точка имеет собственный `slotKey` с суффиксом окна:
```
reminderSlotKey = `${planDate}:${baseTimeHHmm}:reminder:${windowIndex}`
```

Это значит:
- Повторная генерация плана того же дня создаёт idempotent-запись через `planStore.upsertPlanned()` — без дубликатов.
- При каждом исполнении напоминания исполнитель делает отдельный `dispatchLogStore.reserve(reminderSlotKey)` — только для отслеживания факта отправки напоминания, без создания карточки CRM.
- `buildSlotKey()` (`dispatchService.js:21`) не меняется — используется для первичной точки. Для напоминаний применяется расширенный ключ с суффиксом.

#### 4.2.5 Алгоритм детерминированного выбора времени (без изменений vs v1.0)

Для каждого окна (первичного и эскалационного) применяется тот же детерминированный алгоритм:

```
function pickRandomMomentInWindows(planDate, azsId, singleWindowArray, tz):
  seed = hash(planDate + ":" + azsId + ":" + windowIndex)
  rng = makeSeededRng(seed)
  // ... (алгоритм из v1.0, раздел 4.2)
  return baseTime  // HHMM, детерминированный
```

Seed расширен суффиксом `":windowIndex"` — это гарантирует, что момент в окне[0] и момент в окне[1] для одной АЗС независимы.

**Seed**: `djb2(planDate + ":" + azsId + ":" + windowIndex)`. ⚠️ ПРЕДПОЛОЖЕНИЕ — подтвердить с разработчиком: использовать ли `crypto.createHash('sha256')` или простой `djb2`?

#### 4.2.6 executeAt и slotKey для режима B

После получения `baseTime` (HHMM):
```
executeAt = buildZonedDatetime(planDate, baseTime, timezone)  // dispatchPlanGenerator.js:87
// jitterMinutes = 0 — случайность уже в выборе момента
```

`computeExecuteAt()` (`dispatchPlanGenerator.js:172`) вызывается с `jitterMinutes: 0` и без `workWindow` (clamp не нужен — момент уже внутри окна).

#### 4.2.7 Валидация окон (без изменений vs v1.0)

При сохранении настроек (`PUT /api/settings`):
- Каждое окно: `from` и `to` — строки HH:MM (0:00–23:59), `from < to`
- Суммарная длина всех окон ≥ 15 минут
- Минимум 1 окно (первичная отправка обязательна)
- Окна не должны пересекаться: ⚠️ ПРЕДПОЛОЖЕНИЕ — нужна ли строгая валидация или достаточно предупреждения?

## 5. Миграция и обратная совместимость

### 5.1 Стратегия

**Нулевой шаг**: при старте сервера, если в настройках нет поля `dispatchProfiles` (или оно пустой массив), вся система работает **как раньше** — генератор использует `settings.report.dispatchTimes` + `dispatchJitterMinutes` для всех АЗС.

**Опциональное добавление**: администратор создаёт профили через UI. АЗС, добавленные в профиль, начинают работать по профильному расписанию. Остальные → по глобальному.

### 5.2 Что меняется в generateDailyPlan

```
// СЕЙЧАС (dispatchPlanGenerator.js:221-222)
const baseTimes = normalizeBaseTimes(settings?.report?.dispatchTimes)
const jitterLimit = Number(settings?.report?.dispatchJitterMinutes || 0)

// ПОСЛЕ: per-candidate конфиг
for (const candidate of candidates) {
  const profile = resolveProfileForAzs(candidate.azsId, settings.dispatchProfiles)
  if (profile.mode === 'A') {
    // baseTimes из profile.config.slots, jitter из profile.config.jitterMinutes
    // цикл по baseTimes — без изменений vs текущая строка 242
  } else if (profile.mode === 'B') {
    // Первичная точка (окно[0]):
    //   baseTime = pickRandomMomentInWindows(planDate, azsId, [windows[0]], tz, 0)
    //   jitter = 0, entryType = 'primary'
    // Напоминание-точки (окна[1..N-1], если escalateUntilDone === true):
    //   for (let i = 1; i < windows.length; i++):
    //     baseTime = pickRandomMomentInWindows(planDate, azsId, [windows[i]], tz, i)
    //     jitter = 0, entryType = 'reminder', windowIndex = i
    // deadlineAt = buildZonedDatetime(planDate, windows[N-1].to, tz) + graceMinutes
  }
  // planStore.upsertPlanned() вызывается для каждой точки — строка 252
}
```

**Формат записи в dispatch_plan**: таблица дополняется двумя полями — `entry_type` (`'primary'` | `'reminder'`) и `window_index` (integer, 0 для первичной). `base_time` заполняется всегда — для режима B это детерминированно вычисленный момент в виде HHMM.

### 5.3 Что меняется в настройках (defaultSettings.js)

Добавляется поле в `DEFAULT_SETTINGS`:
```js
// NEW
dispatchProfiles: []
```

Добавляется валидация `dispatchProfiles[]` в `validateSettings()` — проверка структуры каждого профиля.

### 5.4 Что остаётся неизменным

- `settings.report.dispatchTimes` / `dispatchJitterMinutes` / `workWindow` — не удаляются, работают как конфиг профиля «По умолчанию»
- `buildSlotKey` (`dispatchService.js:21`), `pickJitterMinutes` (`dispatchService.js:30`), `buildZonedDatetime` (`dispatchPlanGenerator.js:87`), `computeExecuteAt` (`dispatchPlanGenerator.js:172`) — не меняются
- `dispatchService.dispatchBatch()` / `dispatchCandidate()` — не меняются для первичных точек режима B; напоминания вызывают `notificationService.notify()` напрямую, минуя создание карточки
- `timeoutWatcher.runOnce()` (`timeoutWatcher.js:38`) — не меняется; для режима B корректно работает, т.к. дедлайн = конец последнего окна, и watcher не пометит «просрочен» раньше времени
- Механизм идемпотентности через `dispatchLogStore.reserve()` — не меняется

## 7. Критерии приёмки (AC)

### AC-1: Обратная совместимость
- Установка без `dispatchProfiles` (или пустой массив) работает идентично текущему поведению
- Тест: генерация плана без профилей → plan содержит записи для всех АЗС с временами из `dispatchTimes`

### AC-2: Профиль режима A
- Создать профиль с `mode: A`, `slots: ["09:00"]`, `jitterMinutes: 10`, назначить АЗС #42
- После генерации плана: АЗС #42 имеет запись с `base_time = "0900"`, `execute_at` в диапазоне [08:50, 09:10] в таймзоне настроек
- АЗС не из профиля: работает по глобальному расписанию

### AC-3: Профиль режима B — детерминированность
- Создать профиль с `mode: B`, `windows: [{from:"13:00",to:"16:00"}]`, АЗС #117
- Сгенерировать план дважды для того же `planDate` — `execute_at` совпадает в обоих запусках
- `execute_at` попадает в диапазон 13:00–16:00 в таймзоне настроек

### AC-4: Профиль режима B — «не в пик»
- Задать окна, исключающие часы 11:00–13:00 и 17:00–19:00
- `execute_at` для всех АЗС профиля не попадает в исключённые диапазоны (по 100 случайных дат/AZS-ID)

### AC-5: Идемпотентность — режим B
- Запустить `generateDailyPlan` + `dispatchBatch.reserve()` дважды для той же даты/АЗС в режиме B
- Второй вызов возвращает `{ duplicate: true }`, новая запись в `dispatch_log` не создаётся

### AC-6: Одна АЗС — один профиль
- UI не позволяет добавить АЗС в два профиля (занятые АЗС серые/disabled в мультиселекте)
- Бэкенд-валидация при сохранении: `dispatchProfiles` не содержит одну `azsId` в двух профилях → 400

### AC-7: Валидация окон режима B
- Сохранить профиль с `window.from >= window.to` → 400, сообщение об ошибке
- Сохранить профиль с суммарной длиной окон < 15 минут → 400
- Пустой массив `windows` → 400

### AC-8: UI — мультиселект АЗС
- Список АЗС в форме профиля загружается из CRM
- Уже занятые АЗС недоступны для выбора

### AC-9: Миграция — профиль «По умолчанию»
- После добавления нового профиля с несколькими АЗС: оставшиеся АЗС (не в профиле) получают расписание из `settings.report.dispatchTimes` (режим A, глобальный)

### AC-10: Timezone per profile
- Профиль с `timezone: "Asia/Yekaterinburg"` генерирует `execute_at` относительно UTC+5, не UTC+3
- Профиль с `timezone: null` использует `settings.timezone`

### AC-11: Эскалация — напоминание при несданном отчёте
- Создать профиль режима B с 2 окнами: `windows: [{from:"08:00",to:"10:00"},{from:"14:00",to:"16:00"}]`, `escalateUntilDone: true`, АЗС #42
- Сгенерировать план: должны появиться 2 записи — `entry_type='primary'` (в окне 1) и `entry_type='reminder'` (в окне 2)
- Смоделировать наступление окна 2, отчёт НЕ сдан → исполнитель отправляет повторное уведомление по тому же `reportItemId`
- Новая CRM-карточка НЕ создаётся (проверяется по числу вызовов `bitrixClient.createReportItem`)

### AC-12: Эскалация — пропуск напоминания при сданном отчёте
- Та же конфигурация, что в AC-11
- Смоделировать: АЗС сдала отчёт (статус `done`) до наступления окна 2
- При наступлении окна 2: исполнитель проверяет статус → `done` → уведомление НЕ отправляется
- Число вызовов `notificationService.notify` = 1 (только первичная отправка)

### AC-13: Дедлайн режима B = конец последнего окна
- Профиль с 2 окнами: конец окна[1] = 16:00
- После первичной отправки (в окне[0]): `dispatch_log.deadline_at` = 16:00 в таймзоне настроек (± грейс)
- `timeoutWatcher.runOnce()` НЕ помечает отчёт «просрочен» до 16:00, даже если `timeoutMinutes` из `settings.report` истёк бы раньше

### AC-14: Идемпотентность напоминаний
- Запустить генерацию плана 2 раза для одной даты/АЗС в режиме B с 2 окнами
- Второй запуск: `planStore.upsertPlanned()` для напоминание-точки возвращает тот же результат (нет дублей)
- При исполнении напоминания второй раз (если крон-тик повторился): `dispatchLogStore.reserve(reminderSlotKey)` возвращает `{ reserved: false }` → уведомление не отправляется дважды

## 8. Открытые решения

### OR-1: Режим B — один отчёт с эскалацией (РЕШЕНО)
**Решение продакта:** «1 отчёт/день, но если не сдан в первом слоте — обязательно спросить повторно во втором.»  
Эскалация реализуется через напоминание-точки в плане (не новые карточки). Дедлайн = конец последнего окна.  
**Статус:** РЕШЕНО. Зафиксировано в разделах 4.2, 5.2, AC-11–AC-14.

### OR-2: Гранулярность выбора АЗС (РЕШЕНО)
**Решение продакта:** выбор АЗС — поштучно из списка (мультиселект). Группы по региону/тегу — явно «вне scope v1 / возможное расширение v2».  
**Статус:** РЕШЕНО.

### OR-3: Дни недели (РЕШЕНО)
**Решение продакта:** окна/слоты одинаковы каждый день. Различие будни/выходные — «v2».  
**Статус:** РЕШЕНО.

### OR-4: Одна АЗС — один профиль (РЕШЕНО)
**Решение продакта:** одна АЗС максимум в одном профиле; остальные → профиль «По умолчанию».  
**Статус:** РЕШЕНО. Зафиксировано в разделе 3.3, AC-6.

---

### ⚠️ OR-5: Детерминированный RNG (техническое, к подтверждению разработчиком)
**Предложение:** `djb2(planDate + ":" + azsId + ":" + windowIndex)` → seed для mulberry32.  
Альтернатива: `crypto.createHash('sha256')` — более надёжный, но зависимость от Node.js crypto.  
К подтверждению с разработчиком: достаточно ли djb2 для данного использования?

### ⚠️ OR-6: Проверка «не сдан» в точке эскалации — по локальному статусу или по CRM-стадии?
**Вопрос:** при наступлении напоминание-точки исполнитель проверяет `reportsStore.getBySlotKey()` → `report.status`. Однако статус в локальной БД обновляется только при `/submit` через приложение. Если пользователь изменил стадию напрямую в CRM — локальный статус может не совпасть.  
**Предлагаемый дефолт:** проверять локальный `status` (быстро, без доп. вызовов к Bitrix API). CRM-стадию не запрашивать при каждом тике.  
К подтверждению с разработчиком и продактом.

### ⚠️ OR-7: Грейс-период после последнего окна
**Вопрос:** нужен ли грейс (N минут) после конца `windows[N-1]` перед тем, как `timeoutWatcher` бракует отчёт?  
**Предлагаемый дефолт:** 0 минут (без грейса). Дедлайн = точно конец последнего окна. После этого `timeoutWatcher.runOnce()` (`timeoutWatcher.js:38`) бракует как сейчас.  
Возможно добавить опциональное поле `graceMinutes` в конфиг режима B в будущем.  
К подтверждению с продактом.

### ⚠️ OR-8: Что если АЗС вообще не открыл задание к концу последнего окна?
**Предлагаемый дефолт:** после конца `windows[N-1]` + грейс (OR-7, дефолт 0 мин) → `timeoutWatcher` помечает статус `expired`, отправляет уведомление проверяющему (`timeoutWatcher.js:152–163`). Это поведение идентично режиму A — без изменений кода watcher.  
К подтверждению с продактом.

### ⚠️ OR-9: Проверка непересечения окон в режиме B
**Предлагаемый дефолт:** не проверяем строго. Пересекающиеся окна увеличивают вероятность момента в области перекрытия, но не ломают алгоритм.  
К подтверждению с продактом: нужна ли валидация или достаточно UX-предупреждения?

## 9. Вне scope (что НЕ делаем сейчас)

- Группы АЗС по тегу/региону/городу в UI (OR-2, РЕШЕНО → v2)
- per-weekday расписание (разные окна в разные дни недели) (OR-3, РЕШЕНО → v2)
- Несколько независимых отчётов в день в режиме B (режим «по отчёту в каждом окне»)
- Отдельная API-ручка для CRUD профилей (всё через `PUT /api/settings`)
- История изменений профилей / аудит-лог
- Автоматическая перегенерация плана при изменении профиля (ручная регенерация через «Сформировать план»)
- Push-уведомление админу при изменении профиля
- Визуализация расписания (timeline по часам)
